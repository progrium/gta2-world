# Script command reference: missions

- **System:** The runtime commands that start and end a mission, the gang-phone gate that decides whether a mission can even be offered (and shows one of several canned explanations when it can't), the generic timed "bonus challenge" mechanism, and the kill-frenzy weapon template built on top of it. This is the last slice of the script command reference (`mission-scripts.md` §7's split); with it, every command family that split document called for is written.
- **Out of scope:** the mission-bookkeeping *declarations* applied once at level start — the mission-in-progress flag pointers, finish score, mission/secret totals, completion-tracking counters, the death-message base, the crane power-up link, and the "basic keyframe" slot list — already fully covered by `script-declarations.md` §2.16. The mission-fail-on-death-or-arrest rule itself (`mission-scripts.md` §3.3) and the gosub-unwind mechanics behind GOSUB/RETURN (`script-flow-control.md` §2.3) — this note only connects how a mission command sets up what those rules act on. The generic per-ped/per-car/per-object creation commands a mission uses to populate itself, and the mission cleanup list's own per-entity membership rules — `script-cars.md`, `script-characters.md`, `script-objects.md` (including that family's own forced-cleanup command, type 444). The score, cash, lives, multiplier, and wanted-level commands a mission pays a reward or sets a mission beat with — `script-player.md`; the kill-frenzy weapon grant/clear commands usable outside the template below — `script-characters.md`. The on-screen message, brief, timer and counter display mechanism — `script-messages.md`, reused here. Counter variables themselves — `script-counters.md`, reused here for a mission's own pass/fail/in-progress bookkeeping.
- **Builds on:** `mission-scripts.md` (file format, thread/tick model, the fail-unwind rule, triggers), `script-declarations.md` §2.16 (the mission-bookkeeping declarations this note's commands read and update), `script-player.md` (reward commands), `script-messages.md` (display commands, reused directly by the kill-frenzy template), `script-counters.md` (a mission's own pass/fail/in-progress flags are ordinary counters), `script-flow-control.md` (GOSUB/RETURN), `scoring.md` (the score-add formula a bonus reward reuses, and that note's own open question about what consumes its bonus events), `gangs-and-respect.md` (the respect scale the gang-phone gate checks against), `power-ups-death-and-arrest.md` (bonus stages as a distinct, non-script concept — see Open questions).
- **Sources read:** the decompilation's mission-launch helper and the two commands that call it (a direct "launch this mission" command, and the gang-phone gate that decides whether to offer one at all); the mission-end command (shared with RETURN) and the separate mission-cleanup command and the cleanup-list mechanism it drives; the generic timed "bonus challenge" tracker (allocating a challenge, matching a game event against it, paying its reward, and reading its result) and the three small command families built on it (starting one, checking its result, reading its live progress into a counter); the kill-frenzy weapon template's two commands and the save-game bit they set; and the one declared-but-dead command type sitting in the same numeric neighbourhood.
- **Date and author:** 2026-11-20, Claude (notes writer, reader side).

Tags: **[scr]** the compiled script file format, **[exe]** fixed in the executable, **[obs]** to confirm in play.

## 1. What the player sees

Getting into a trigger car or walking into a trigger area can start a mission immediately. Answering certain phones is different: the gang on the other end only offers a mission if the player isn't already running one of theirs, hasn't already passed or failed the one on offer, and has enough respect with that gang — otherwise the phone just plays one of several canned "come back later" / "you need more respect" / "you're already on a job" lines instead of starting anything. A mission that finishes pays out with an ordinary score, cash, life, or multiplier bonus (whatever the mission script itself chooses to grant) and tidies up anything it spawned along the way. Separately, walking over a kill-frenzy pickup (or being offered one some other way) flashes "KILL FRENZY!" on screen with its own voice line, hands the player a special time-limited weapon, and starts a countdown clock and a target counter: kill or destroy enough of whatever the challenge calls for before time runs out, and it pays a reward and clears the wanted level; run out of time (or die, or get arrested) first, and it just ends with nothing. Only one kill-frenzy challenge can be running anywhere in the level at a time.

## 2. Inputs: the mission commands [scr]

These commands run like any other script command (`mission-scripts.md` §3.2): one per tick, in thread order, as the thread's current command. The "looked up by command number" convention from `script-declarations.md` §2 still applies throughout.

### 2.1 Starting a mission

| Type | Parameters | Effect |
|---|---|---|
| 274 | a mission sub-script's name (via the string table) | Loads that mission sub-script (`mission-scripts.md` §2's per-mission file, loading it from disk now if it wasn't preloaded) and jumps into it with a GOSUB (`script-flow-control.md` §2.3) — not a new thread. The command right after this one is where execution resumes once the mission eventually returns. |
| 263 ("gang phone gate") | a base brief-message id, a "passed" flag and a "failed" flag (each an earlier-declared counter the mission itself sets, see Edge cases), four "currently on a mission" flags (one general, one per gang 1/2/3 — again plain counters, in practice the same ones the level-start declarations point the mission-in-progress flags at, `script-declarations.md` §2.16), a gang name, a required respect level, and the names of two mission sub-scripts ("mission 1" and "mission 2") | The gang-phone gate described under "What the player sees." Checked in order: if the player is already on a mission for gangs 1, 2, or 3, or has already passed or already failed the mission on offer, shows one of several fixed brief messages (built from the base id plus a per-situation offset, see Numbers) explaining why, and does nothing else. Otherwise, if the player's respect with the named gang (converted to the same ±20-per-step units `gangs-and-respect.md` §3.2 uses) is at least the required level, clears the "did the last mission just fail" flag (`script-player.md` §2.5) and launches "mission 1" the same way type 274 does (or "mission 2," once the player has already passed or failed once — see the passed/failed branches above, which launch mission 2 instead of showing their explanation when respect is high enough). If respect is too low, shows a different explanation depending on whether it's exactly zero, negative, or just not quite enough. |
| 272 | none found | Declared in the command-type table but has no handler of any kind, at level start or at runtime — reaching it as a thread's current command does nothing and just advances, the same as any other unrecognised type. See Edge cases and Open questions. |

### 2.2 Ending a mission

| Type | Parameters | Effect |
|---|---|---|
| 273 | none | Shares its handler outright with RETURN (`script-flow-control.md` §2.3): pops the thread's top gosub frame and resumes wherever that frame was called from. Writing "end the mission" in a mission script compiles to exactly the same instruction as an ordinary subroutine return. |
| 391 | none | Force-cleans-up the mission: every car, ped and object the mission's own runtime creation commands registered to the mission cleanup list (`script-cars.md`, `script-characters.md`, `script-objects.md` §2's runtime creation types, plus that family's own type 444 for anything forced in early) is despawned, stopped-and-marked-for-removal, or deleted, respectively; the player's own follower group (if any) is disbanded; and a level-wide "this car model is wanted" marker (unclaimed by any other note — see Open questions) is cleared back to none. A mission typically runs this as one of its last lines, before returning or hitting mission-end. |

### 2.3 Timed bonus challenges

A reusable mechanism, not specific to kill frenzies: define a target (kill enough peds of some kind, or destroy enough cars of some kind) within an optional time limit, and get told later whether it was reached. Up to 10 such challenges can be tracked at once for the player (see Numbers); each is attached to its own command number the same self-referencing way `script-declarations.md` §2 describes.

| Type | Parameters | Effect |
|---|---|---|
| 288 / 289 / 290 / 291 | an optional zone name (restricting the challenge to one map zone), a target count, an "exclusive" flag, what counts (a car model, a ped occupation, or a gang's cars/members — one of four shapes chosen by a parameter, not by which of these four types is used; all four behave identically), a second, alternate target for the "car model" shape, a time limit (or none), a required vehicle the player must be driving at the moment of the kill or destruction (or none, for no such requirement), a reward amount, and (for ped kills) a required cause of death (or any) | Starts tracking a challenge: every matching kill or car-destruction credits it one step closer to the target count. A handful of "kind" values are treated as groups rather than single exact matches — some similar car models count for each other (for example the game's two taxi variants, or its several police/military vehicles), and some ped occupations are wildcard groups (any law-enforcement occupation, any emergency-service occupation, any gang member, any Elvis impersonator); a cause-of-death group works the same way (for example "any explosion," covering several specific causes). With the "exclusive" flag on, any other matching-category event (any other kill, or any other car destroyed) that *doesn't* fit this challenge's own filters cancels it outright instead of just being ignored. The moment the target count is reached, the reward is paid immediately as score (the same multiplier-scaled add `scoring.md` §3.1 and `script-player.md` §2.1 use) — a script doesn't need to check the result for the reward to land (see Edge cases, and `scoring.md`'s own open question about what consumes its bonus events). In the French version, a challenge that targets a law-enforcement vehicle model or occupation is silently neutralised to match nothing, the same blanket rule `scoring.md` §3.2 already documents for ordinary police kills. |
| 292 / 293 / 294 | an earlier "timed bonus challenge" command | A condition: true if that challenge has been resolved as passed (292), resolved as failed — by running out of time, by an exclusive-mode mismatch, or by being cancelled (293), or resolved either way, i.e. no longer in progress (294). Once resolved, the result is remembered, so asking again later still gives the same answer even though the challenge's own internal slot has by then been freed for reuse. |
| 402 | an earlier "timed bonus challenge" command, a counter | While the challenge is still in progress, writes its live progress count into the counter. Once the challenge has resolved, its progress count is no longer available (the slot that held it has been freed), so this quietly stops updating the counter — it's left holding whatever it last had. |
| 401 | — | Declared in the command-type table but has no handler anywhere, the same dead-code pattern as 2.1's type 272. See Open questions. |

### 2.4 The kill-frenzy weapon template

Built on top of 2.3's challenge mechanism. Type 422 is dual-purpose: at level start it's one of `script-declarations.md` §2.16's declarations (reserving a "basic keyframe" slot); reached later as a thread's current command, it's where the actual kill-frenzy behaviour lives.

| Type | Parameters | Effect |
|---|---|---|
| 422 | the trigger this came from, a brief-message id, an object to remove (typically the kill-frenzy pickup icon), the player, and a weapon | If a kill-frenzy challenge is already running anywhere in the level (a single level-wide flag, see Numbers), re-enables the trigger that led here and ends the thread the same way a RETURN with an empty gosub stack does — so the player can try again once the current one finishes. Otherwise, commits: marks the level-wide flag, disables its own trigger (so it can't double-start while running), shows a fixed "KILL FRENZY!" banner message with its own voice line, removes the named object if it turns out to be one (the pickup icon, typically), queues the given brief message, arms the player with the given weapon — a hand weapon or, if it's one of the vehicle weapons, a weapon mounted on the player's current car (the same effect as `script-characters.md`'s own weapon-grant commands, types 411/412) — and records in the save game that this level's basic-keyframe slot (the one this same command number reserved at level start) has now been started, so reloading a save won't let its trigger fire again from scratch. |
| 423 | an earlier "timed bonus challenge" command (2.3) defining the actual target, an earlier countdown-timer command and the time limit to give it, an earlier on-screen-counter command and the counter it's bound to, the challenge's target count again, an unused brief-message id (see Edge cases), the player, a reward kind (score, multiplier, or lives), and a reward amount | The kill-frenzy challenge's per-tick body (see Rules for how it holds the thread). First tick: creates the countdown timer and binds the on-screen counter, using the same shared display slots `script-messages.md` §2.6–2.7 documents, just set up directly rather than through those commands. Every tick after that, while the named challenge (2.3) is still in progress: updates the on-screen counter to show the target count minus the challenge's current progress; if the player has died or been arrested, cancels the challenge early and takes back the special weapon. Once the challenge has resolved: clears the shared timer/counter display, takes back the special weapon regardless of how it ended, and clears the level-wide "a kill frenzy is running" flag so the next one can start. On a pass: shows a fixed "frenzy passed" message and voice line, clears the player's wanted level, counts the level's "secrets passed" total up by one (`script-declarations.md` §2.16), and pays the given reward as score, a multiplier change, or a life-count change (reusing exactly the effects `script-player.md` §2.1–2.2 document for its own score/multiplier/lives commands). On a failure: shows a fixed "frenzy failed" message and voice line, and counts the level's "secrets failed" total up by one instead. |

### 2.5 Bonus-stage start/end

No such script command exists. A "bonus stage" turns out to be a property of which level is loaded — set when the player picks one from the frontend's stage-select screen, not something a mission script starts or ends mid-level. The only place any note needs it is already covered: `power-ups-death-and-arrest.md` §3.3 already documents that dying or getting arrested during a bonus stage (or with no lives left) ends the level as game over, same as running out of lives elsewhere. See Open questions.

### 2.6 Rewards

There's no dedicated "pay a mission reward" command. A mission pays out by using the same commands any other script line would: `script-player.md` §2.1's score/cash commands (with or without the multiplier) and §2.2's life-count command, or 2.4's kill-frenzy reward above, which reuses those same effects directly rather than calling the script commands themselves.

### 2.7 Retrying a mission

There's no dedicated "retry" command either. 2.1's gang-phone gate is the whole mechanism: a mission sets its own "passed" or "failed" counter (an ordinary `script-counters.md` §2.2 "set a counter" command) as one of its last lines, and the next time the same phone is answered, the gate reads that same counter and offers the follow-up mission instead of the first one (or just explains why not, if respect is too low).

## 3. Rules

- **Starting a mission adds exactly one level of gosub nesting**, whichever of 2.1's two commands does it — it's a GOSUB into the mission's own entry point, not a new thread, so the mission runs as a subroutine of whatever thread triggered it (a phone, car, or on-foot trigger thread, `mission-scripts.md` §3.4). `mission-scripts.md` §3.3's forced-fail path assumes exactly two levels of nesting are active when it unwinds; this note's commands only account for the one level that gets the mission running at all. What supplies the second level — presumably something inside a mission's own body — is outside this note's sources and is still open on `script-flow-control.md`'s side (its own Open questions already flag this from the other direction).
- **A mission sets its own in-progress flag.** `script-declarations.md` §2.16 only says which counter the general and per-gang "mission in progress" flags are — it's the mission script itself that sets that counter to a nonzero value right after being launched and clears it again before it ends, using an ordinary `script-counters.md` §2.2 command. The engine only ever reads it (`mission-scripts.md` §3.3's fail check, and 2.1's gang-phone gate above).
- **2.4's kill-frenzy body (type 423) doesn't advance itself while its challenge is still running.** Every other command in the reference either does its effect and moves on in the same tick, or uses one of `script-flow-control.md`'s own wait/delay/loop idioms to hold the thread in place. This one does neither: on any tick where it has nothing new to report (still waiting on its first-tick setup to matter, or the underlying challenge hasn't resolved yet), it simply doesn't call the "advance to next command" step at all, so the thread's current command stays this same line until the challenge resolves. Reproduce it as its own small state machine, not as a disguised wait-here.

## 4. Order of events

- **Starting a mission:** whichever of 2.1's commands runs, in order — load (if needed) and gosub into the mission sub-script; the triggering thread's own next line only runs once the mission eventually hits mission-end or RETURNs (or, for the gang-phone gate, once that same gate is answered again later and nothing's currently blocking a new mission).
- **A kill-frenzy challenge, tick by tick:** 2.4's type 422 runs once, on the tick the trigger fires (committing or deferring). From the next tick it's reached, 2.4's type 423 runs every tick: set up the display once, then poll every tick after that until the underlying 2.3 challenge resolves, then tear down and pay out in one final tick before finally advancing.
- No further ordering beyond the general thread rule (`mission-scripts.md` §3.2): each of these commands is an ordinary one-tick command except where noted above.

## 6. Edge cases and quirks worth reproducing

- **The gang-phone gate's "already on a mission" check has a flag with no message of its own.** It checks all four "currently on a mission" flags (general plus gang 1/2/3) before even looking at the passed/failed flags, but only the three gang-specific ones get their own explanatory brief. If only the general flag is set (the player is on some mission, but not specifically one of this gang's), the gate falls straight through to the respect checks as if nothing were in progress at all.
- **A kill-frenzy challenge's progress counter becomes unreadable at the same moment it resolves.** `script-counters.md`'s general comparison/arithmetic commands could, in principle, still name the counter this challenge's progress was being mirrored into (2.3, type 402) — but the moment the underlying challenge resolves, its own progress count is gone, so that mirroring command silently stops updating and the counter just keeps whatever value it last had.
- **2.4's per-tick command (type 423) takes a second brief-message id parameter that's never read by anything.** Every other parameter on this command is used somewhere in its handling; this one isn't. Flagged rather than guessed at — see Open questions.
- **The "basic keyframe" declaration (`script-declarations.md` §2.16, type 422) is this note's own kill-frenzy trigger, not an animation.** That note correctly describes its level-start effect (reserving a slot in a 25-entry list) but couldn't tell what the reserved thing was for. It's this family: at runtime, the same command number both starts the kill frenzy and records its own position in that same list into the save game, purely so a reload remembers which kill-frenzy triggers have already fired and keeps them disabled.
- **A declared command type with no handler anywhere (2.1's type 272, and 2.3's type 401) does nothing at all** if a compiled script somehow reached it — not an error, just a silent no-op advance, the same dead-code pattern `script-flow-control.md` and `script-counters.md` both already found in their own families.

## 7. Open questions

- **What supplies the mission-fail path's second level of gosub nesting**, beyond the one level 2.1's launch commands add. `script-flow-control.md` already flags this from its own side; nothing in this pass's sources settled it either.
- **Whether type 272 or type 401 are truly unreachable**, or whether some compiled level still emits one of them, the same caveat `script-flow-control.md` and `script-counters.md` give their own dead types.
- **What the unused brief-message parameter on 2.4's type 423 was meant to show.** Every other field on that command is read by its handler; this one plainly isn't.
- **What the level-wide "this car model is wanted" marker that mission-end (2.2, type 391) clears is actually for.** It's set by a command this note's sources couldn't place in any family that's been written yet (not clearly mission bookkeeping, not clearly player state) — flagging it here only because mission-end happens to clear it, not because this note claims the command that sets it.
- **Whether "bonus stages" (2.5) interact with any script command at all.** This pass found them read only as a property of the loaded level (by the death/arrest/game-over logic `power-ups-death-and-arrest.md` already documents) and set only from the frontend's stage-select screen — never by anything in the script command dispatch. Flagging as a confirmed negative finding rather than a gap, in case a later pass over the frontend or save-game code finds a script-facing hook this one missed.
